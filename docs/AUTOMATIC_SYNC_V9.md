# v9：普通权限游戏的自动检测

2026-10-09 UTC。用户明确游戏不会以高权限运行，因此本轮按当前账户普通权限游戏收窄检测；不再要求下载或运行独立探针。

## 检测范围

- 无可执行身份、也没有当前或已观察游戏关联证据的受限进程不再阻止上传/恢复。
- 所选官方 JAR、已知 Shattered 主类与原生候选仍拦截；已关联游戏信息丢失、进程枚举失败仍停止操作。
- 已知 Java 进程参数完全不可读时仍停止；可读的其他 JAR 通过有界主类检查区分，保留改名游戏 JAR 的识别。
- 每次检查重新枚举；同一应用、同一目标的检测器保留有界 PID/启动身份关联，目标变更重建。不访问被拒绝的可执行身份路径，不改变系统权限。
- 这不是全局写入锁，不覆盖其他账户、高权限游戏或任意隐藏/自定义启动器。Steam Cloud 等仍应避免同时写入。

自动上传、不可变计划与真实基线、静默和重复指纹检查、恢复前备份、版本守卫、显式冲突选择、双按钮及设备/时间元数据均保留。新元数据共享客户端仍须一起升级。

## 验证

- 完整 `build :core:installDist --offline --no-daemon` 通过，373 JVM 测试（341 核心 + 32 桌面）零失败/错误/跳过；3 Python 测试通过。
- 46 个聚焦检测/稳定性测试通过；额外 8 个独立对抗测试通过，含无关联受限辅助进程、改名游戏 JAR、枚举失败、离线计划、恢复竞态和调度器。
- 云端 Linux **真实生产入口** `pdsync.MainKt` 成功完成登录、手动上传、文件变更自动上传。运行副本与构建 JAR 哈希一致，不含测试注入类/测试 classpath。
- 在同一云桌面启动普通权限官方 Shattered 4.0.2 JAR（独立游戏数据目录）。同步器检测运行，手动上传被阻止，合成文件变化超过 30 秒仍未发布；仅正常关闭本轮新启动的游戏后自动上传恢复。
- 最终生产构建无勾选恢复成功：先备份第三份合成字节，再恢复第一份字节；恢复提交自动发布，原快照来源/采集时间保留，操作时间独立，真实父提交链正确。等待后无自触发重复发布。
- 首次恢复尝试曾遇到暂时 Unknown 并安全拒绝，文件和提交未变化；当时正进行另一个构建，具体触发进程未确定。状态恢复后，在最终冻结生产构建中明确重新确认并成功。没有将失败记录作通过证据。
- 设置显示普通权限检测假设，暂停仍保留手动上传。全部 UI 流程只有一个应用主窗口。

详细记录、JUnit XML、闭合事件日志、截图及字节级检查摘要在 [本轮证据](automatic-v9-evidence/UI_VALIDATION.md)。历史 v8 注入验证只作为历史记录保留，不用于本轮生产守卫验收。

## 验证边界

真实游戏仅用于运行/退出进程守卫，上传/恢复对象是独立合成存档，服务是隔离 loopback demo。不能据此声称恢复后的合成内容能被游戏载入，也不能声称本轮真实 Cloudreve 或跨设备完成。使用进程级软件渲染与已有字体配置；Windows/macOS 原生、默认 GPU 路径、断电事务、恶意 TOCTOU、任意自定义启动器、其他账号/高权限游戏与 Steam Cloud 互斥仍未证明。用户电脑及其旧应用/服务未被本轮修改。
