# 快照来源、设备与时间元数据

新客户端在原 `Manifest.schema=1` 归档结构中添加可选 `metadata`，在 `AppendCommit.schema=2` 中添加可选 `operation`。两个扩展均明确写入自身 `version=1`，未知扩展版本、字段、超限内容及无效时间/设备身份会被拒绝。协议 DAG、文件哈希、ZIP 内容和随机对象 ID 的职责保持不变。

## 来源与操作分别记录

- `metadata.device`：原快照采集设备的随机持久 UUIDv4 与设备名称。
- `metadata.capturedAt`：采集时设备时钟提供的规范 UTC 时间。
- `metadata.fileModifiedAt`：逐文件的原始文件修改时间，使用 UTC。它不是采集时间，也不是云端上传时间。
- `operation.device` / `operation.preparedAt`：新提交由哪台设备、在何时准备。恢复和冲突选择复制原快照来源，另外记录当前操作设备/时间，不会把旧快照假称为当前设备的新进度。
- 本地历史 `savedAt` 是加入本机历史的时间；可选 `remoteObservedAt` 和追加仓库单独保存的 `observedAt` 是本机首次成功验证该远端提交的时间。它们不是服务器确认的上传时间，不写入远端不可变提交，不因重试而改写。

发布计划先冻结包括来源、操作信息在内的精确提交字节。失败、重启、恢复重试沿用原计划，不更新其时间或标签。元数据不参与分支胜负、去重内容哈希或因果排序；这些由文件摘要、随机提交 ID 和父 DAG 决定。所有时间都可能有设备时钟偏差，设备/时间也不是可信的密码学身份声明。

## 设备身份与展示

每个应用状态目录有一份独立 `device.json`，保存随机 UUIDv4。重新启动、换档案和修改设备名称不会换 ID；不同安装/状态目录独立生成 ID。不使用 MAC、硬件序列号、用户名或存档路径派生身份。读到损坏的身份文件时停止，不静默替换。

自动读取系统主机名称作为显示名称，做 Unicode NFC 规范化、移除控制符及方向格式符、折叠空白，限制为 64 个 Unicode 码点，空值使用通用名称。显示时总是附加稳定的 8 位设备 ID，区别重名设备。该名称会随元数据发送到已配置的同步档案；界面应在上传前展示当前设备名称和短 ID。

## 向后读取边界

新客户端可读取没有扩展的旧快照、历史、待上传计划和提交；未知来源继续保持空值，显示“来源未知”，不能从收到时间或文件时间猜测设备/采集时间。旧远端字节不批量升级、不重写；对旧快照执行新的恢复/解决提交时，仅新提交有当前操作信息，旧快照来源仍未知。

旧客户端使用严格 JSON 解码，不能读取带这些新扩展的提交。因此这是新客户端向后读取兼容，并非旧客户端向前兼容。共享同一远端档案的客户端需要一起升级；不能把旧客户端不能读的新提交作为坏对象自动删除或覆盖。

## 验证范围

`SnapshotMetadataTest` 覆盖跨重启身份、同名独立设备、并发初始化、身份损坏、Unicode/控制符边界、采集与文件修改时间区别、原游戏字节保持、旧 JSON 和未知来源、恢复与解决来源/操作分离、精确重试、独立本地观察时间、恶意元数据拒绝、本地历史和备份来源。使用合成存档和内存远端，不代表真实 WebDAV/跨平台系统主机名探测已验证。

### 目录内容 SHA-256

复用适配器选中的游戏内容文件和现有路径安全检查；相对路径统一使用 `/`、保留大小写，拒绝绝对路径、`..`、重复或跨平台别名。明确排除 sidecar 自身和该 sidecar 的临时文件，即使以后适配器扩大文件范围也不纳入内容指纹、游戏文件 ZIP 或恢复删除清单。

以规范相对路径的 UTF-8 字节序稳定排序。每项包含路径及其文件内容 SHA-256，因此文件新增、删除、修改和路径改名都会改变汇总值；枚举顺序、mtime、ZIP 打包时间和用户显示名不会改变它。

建议固定版本的无歧义编码：ASCII 域标记 `PDSYNC-CONTENT-V1` + 4字节大端文件数量；每项依次写4字节大端 UTF-8 路径字节长度、路径字节、32字节文件 SHA-256 原始值。对完整编码再做 SHA-256，存储小写64位十六进制。空目录同样有确定摘要。不要简单拼接路径和摘要，也不要依赖 JSON 字段顺序或分隔符猜边界。算法编码需版本化并与已存在的文件摘要映射一致。

### Sidecar 与名字

在每个存档根目录保存一份 sidecar（建议名 `.pdsync-meta.json`，实施前固定保留名），最小字段为：

- `schema` / `hashAlgorithm`：元数据版本及上述内容摘要编码版本。
- `displayName`：用户自定义名称，空值使用界面默认名。
- `currentContentSha256`：最近一次实际读取计算出的内容摘要，仅作缓存。
- `lastSyncedContentSha256`：上次成功且验证完成的同步内容摘要；没有可靠基线时为 `null`。

名称作为独立同步元数据随对应快照保留，不进入游戏内容摘要；改名只改变显示元数据，不制造“游戏内容未同步”状态。不要将完整 sidecar 当作游戏文件同步，尤其不能把别的设备记录的本地同步基线直接当成本机已同步证明。正式扩展需遵循本文件已有的严格 schema/兼容性规则，不静默改写旧的不可变远端提交。

### 读取、更新与失败语义

每次判断本机是否有修改，都用实际内容重新验证/重算当前摘要，与可靠的 `lastSyncedContentSha256` 比较；不能把缓存的 `currentContentSha256` 或单独的 mtime 当作事实。无可靠基线时状态为尚未建立同步基线，不因内容缓存存在就显示已同步。

成功上传且远端验证通过后，才将实际发布的那份内容摘要写为同步基线；上传期间的新改动继续保持未同步。恢复须完成内容写入、重新读取并验证目标内容之后才能推进基线。失败、校验不通过、进程仍运行、取消和未完成恢复均不推进同步基线。提交基线与 sidecar 的更新有中断或不一致时采取保守状态，不宣称同步完成。

在现有档案锁和安全路径检查下写入同目录临时文件，再原子替换 sidecar；失败保留旧文件和旧基线。`SafePaths.atomicWrite` 可复用其基本结构，但当前不支持原子移动时会降级为普通替换：sidecar 实施时必须明确保证原子替换，不可把该降级路径宣称为原子写入；不支持时应报告失败并保持保守状态。临时文件使用专属可识别保留名并明确排除，不扩大为忽略任意用户文件。

sidecar 缺失或损坏时，可重新计算当前内容摘要；名称未知则用默认名，同步基线不能从当前摘要、目录存在或远端最新节点伪造。只有已有可信、验证过且与该目录对应的同步记录才能用于恢复基线，否则保持未知。不得保存 WebDAV 密码或凭据到 sidecar。

### 待实现：只对内容丢失要求确认

上传与恢复统一以“操作是否会丢失尚未保留的游戏内容”为确认条件。追加上传保留既有云端历史，故不需要覆盖确认；不得将其改成覆盖删除云端历史，也不引入额外备份步骤。

恢复前重新计算本机完整游戏内容摘要（包括游玩记录）。本机为空、当前摘要等于可信上次成功同步基线且该内容仍可恢复，或当前完整内容已在任一经过验证的可恢复云端历史中保留，均不会丢失内容，直接恢复所选目标；目标不必是最新版本，回滚旧版也适用。相同内容保持不重复操作。仅当恢复会覆盖尚未保留到云端的独有本机内容时要求明确确认；保留证明缺失时按可能丢失处理，不能靠名字、时间、文件存在、过期缓存或未经验证的远端声明推定安全。正式实现仍须执行下载、内容完整性、版本及进程检查，并绑定确认时的内容与目标，变化后重新判断。

原型现有 `contentId` 仅模拟上述完整内容hash和已验证云端内容身份；新增“远端更新，本机无改动”场景展示本机连旧云端，新云端位于上方，直接恢复后连接新版本。正式SHA-256与sidecar写入仍待实现。验收补充：远端更新本机未改免确认；当前内容保留于旧云端历史时免确认；缺保留证明或独有记录变化仍确认；改名不改变判断；上传分歧仅追加且免确认。
